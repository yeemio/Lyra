## R22　SENT 态截止先到的终态归属（2026-10-25，总控裁定）

**背景**：P0 验收（`delivery/P0-DELIVERY.md`）发现条款张力：executor 竞速分支在"截止先到、远端结局不明"时落 `FAILED/DEADLINE_EXCEEDED`，与 EK-3.3 字面（中断/失联/截止且无确认终态 → UNKNOWN）冲突，但与 EK-6.2（未按窗完成）自洽。登记为 P1 冻结前须裁定项。

**裁定**：
1. SENT 态截止先到且 modelFn 仍挂起（远端结局不明）→ permit 终态 **UNKNOWN**，`fail_code='DEADLINE_EXCEEDED'`（"未按窗完成"窗口分类由 fail_code 承载，不与 permit 态混同）。处置走 EK-5：不自动重采样、Owner 显式确认后本地退役。
2. modelFn 先解决但晚于 deadline（结果已知但迟到）→ 按实际结果 settle（成功 → SUCCEEDED），`fail_code='LATE_COMPLETED'`（诚实记时，不冒充按窗完成；Metis `late_completed` 先例，SPEC §9.3）；显式错误晚到 → FAILED + 原错误码。
3. 发送前过期 → 维持 FAILED/DEADLINE_EXCEEDED（从未发送，结局已知）。

**理由**：诚实边界——远端可能已产生结果与费用，标 FAILED 宣称了未掌握的知识；Metis 真实先例：`business_deadline_exceeded` 的 J 保持 UNKNOWN、远端结果/费用未知、不重发不退款（`docs/FREEZE` 前身记录见 metis AGENTS 2026-10-23 节）。FAILED 保留给已知结局的失败（显式拒绝、解析失败、模型侧确认错误）。

**落点**：`docs/specs/EXECUTION-KERNEL.md`（EK-3.3/EK-6 条款澄清，〔R22〕标注）；`src/kernel/executor.ts` + `src/kernel/executor.test.ts`（W1 名下回工）；`src/journey/journey.test.ts` EK-10.2.6 用例断言更新（总控名下）。

**实施与验证证据**（2026-10-25 回填）：
